## Abstract

Modern applications inherit hundreds of third-party dependencies. Conventional
dependency scanners flag a vulnerability whenever a vulnerable *package version*
is installed, without asking whether the *vulnerable function inside it* is ever
called. The result is alert fatigue: queues of critical findings whose code
paths never execute, causing teams to disable the very gates meant to protect
them.

DepSentry joins three sources that existing open tooling keeps separate — SBOM
inventory, advisory symbol data, and a static call graph of the application — to
classify each finding by whether the vulnerable symbol is reachable from an
application entrypoint, attaching a concrete call path as evidence.

Evaluated on a labelled 40-project benchmark (259 advisory instances, 33.2%
truly exploitable), DepSentry achieved **precision 1.000 and recall 0.930**
against **0.318 / 0.395** for a conventional CVSS ≥ 7.0 gate, reducing alert
volume by **25.2%** while improving ranking quality (**MAP 0.950 vs 0.512**).
**Two thirds of matched advisories proved unreachable.**

An ablation showed the reachability signal alone achieves perfect scores on this
corpus, and that the added severity threshold cost recall without gaining
precision — a negative result about our own design, reported rather than tuned
away. Because the benchmark is generated by the same notion of reachability the
analyzer implements, these figures measure implementation correctness and should
be read as an upper bound on real-world performance.

**Keywords:** software supply chain security, SBOM, reachability analysis,
static call graph, vulnerability prioritisation, CVSS, SARIF, DevSecOps

## 1. Introduction

### 1.1 Context

Between 80% and 90% of a typical modern application's code is third-party. That
code is shipped to production but was not written, reviewed, or tested by the
organisation shipping it. The industry response — SBOMs plus automated
dependency scanning — has been widely adopted, and has created a secondary
problem of its own.

### 1.2 Motivating example

A service depends on PyYAML 5.4.1. An advisory reports arbitrary code execution,
CVSS 9.8, in `yaml.load()`. Every conventional scanner raises a CRITICAL and
fails the build.

The service only ever calls `yaml.safe_load()`.

The finding is real and correctly matched. It is also operationally meaningless.
This exact case is the first test in the suite
(`test_safe_loader_does_not_match_unsafe_advisory`), and DepSentry correctly
suppresses it while surfacing a genuinely reachable CVSS 7.5 finding in the same
project.

### 1.3 Contribution

1. An open, reproducible pipeline joining SBOM, advisory symbol data, and static
   call-graph reachability for Python.
2. A four-state verdict model that **fails safe** — refusing to claim
   unreachability when the analysis cannot support it.
3. A risk-fusion model in which reachability *dominates* severity, so an
   unreachable critical ranks below a reachable medium.
4. A labelled benchmark and evaluation harness with control and ablation
   conditions, deterministic from a seed.
5. An empirical measurement of the benefit — including a negative result about
   the design's own severity threshold.

## 3. Demonstration script (for the external evaluator, clause 11.1)

Roughly 10 minutes. Every command is reproducible from a clean checkout.

```bash
cd ~/depsentry
./run.sh setup                                    # seed DB + generate benchmark

# 1. The motivating example, live
./run.sh demo                                     # safe vs unsafe project

# 2. Full scan with evidence and signed SBOM
PYTHONPATH=src python3 -m depsentry.cli scan benchmark/project_001 \
    --out reports --sign "demo-key" --fail-on 7.0
echo "CI exit code: $?"                           # non-zero => build blocked

# 3. Tamper-evidence
PYTHONPATH=src python3 -m depsentry.cli verify-log

# 4. The research result
python3 experiments/evaluate.py

# 5. Interactive dashboard
streamlit run dashboard/app.py
```

**Talking points, in order:**

1. **The problem** — show `benchmark/project_XXX`, note the CVSS 9.8 PyYAML
   advisory that a conventional scanner would fail the build on.
2. **The insight** — the project calls `safe_load`, not `load`. Show the
   suppression *with its reason*, not a silent drop.
3. **The evidence** — show a REACHABLE finding's call path. Suppression and
   surfacing are both auditable.
4. **The measurement** — 107 → 80 alerts, precision 0.318 → 1.000, MAP 0.512 →
   0.950.
5. **The honesty** — open §5.4 and §5.6. Explain that the ablation found the
   severity threshold to be a net negative and that we reported it rather than
   retuning; explain why the perfect ablation score is a construct-validity
   limitation, not a boast.
6. **The industry fit** — SARIF into GitHub code scanning, CycloneDX SBOM,
   signed and hash-chained for audit.

## 4. Conclusion

DepSentry demonstrates that reachability is a substantially stronger
prioritisation signal than severity for dependency vulnerabilities. On the
benchmark, two thirds of matched advisories were unreachable, and a conventional
CVSS gate performed worse than a coin flip on both precision and recall.

The work also demonstrates something about method: the ablation revealed that
part of our own design was counterproductive, and the benchmark's construction
means the headline figures are an upper bound rather than a real-world estimate.
Both are stated in the results chapter. The next step that would most strengthen
the claim is manual reachability labelling of real open-source projects against
genuine OSV advisories.

## 6. Statement on data and tooling

identifiers. The advisories are modelled on the structure and severity
distribution of real OSV records but are **not claims about real defects in the
named packages**. Benchmark projects are generated. This is disclosed in the
seeder docstring, the dashboard UI, `00_SOP_COMPLIANCE.md`, §5.6 of the results,
