## 5.1 Experimental design

**Corpus.** 40 generated Python projects, 3–7 dependencies each, four
application archetypes (web API, data pipeline, CLI tool, batch worker).
Deterministic from seed 42.

**Ground truth.** For each (project, advisory) pair the generator decides
whether to emit code that calls the vulnerable symbol or a safe alternative, and
records that decision. The label is therefore correct **by construction** rather
than by inference.

| Corpus property | Value |
|---|---|
| Projects | 40 |
| Advisory instances scored | 259 |
| Truly exploitable (ground truth positive) | 86 |
| Prevalence | 33.2% |
| Pairs excluded as unscored | 22 |

**Exclusion rule.** Only pairs the SBOM matcher actually surfaces are scored.
Advisory *matching* is not the variable under test — *reachability* is — so
pairs that never reach the reachability stage are excluded from every condition
equally. The 22 excluded pairs are advisories whose pinned version fell outside
the affected range.

**Conditions.**

| Condition | Rule | Represents |
|---|---|---|
| `baseline_all` | Flag everything | No triage |
| `baseline_cvss7` | Flag CVSS ≥ 7.0 | The standard CI gate |
| `depsentry` | Flag actionable (reachable ∧ risk ≥ 4.0) | This work |

## 5.2 H1 — Detection performance and alert volume

| Condition | Alerts shown | Precision | Recall | F1 | TP | FP | FN |
|---|---|---|---|---|---|---|---|
| **DepSentry** | **80** | **1.000** | **0.930** | **0.964** | 80 | **0** | 6 |
| Baseline: CVSS ≥ 7.0 | 107 | 0.318 | 0.395 | 0.352 | 34 | 73 | 52 |
| Baseline: no triage | 259 | 0.332 | 1.000 | 0.499 | 86 | 173 | 0 |

Headline figures:

- Alert volume **107 → 80**, a **25.2% reduction** against the CVSS gate, and
  **69.1%** against no triage at all.
- **Zero false positives.** Every finding DepSentry surfaces is genuinely
  reachable.
- Precision gain over the CVSS gate: **+0.682**.
- Recall retained: **93.0%**.

**H1 is supported**, with one qualification carried into §5.4: recall is 93.0%,
not 100%.

### The CVSS gate performs worse than it looks

The most striking result is not DepSentry's score but the **baseline's**. A
CVSS ≥ 7.0 gate achieves precision 0.318 and recall 0.395 — it misses 52 of 86
genuinely exploitable findings while raising 73 false alarms.

That is worse than a coin flip on both axes, and it is the configuration
deployed in a great many real CI pipelines. The reason is structural: CVSS is
**uncorrelated with reachability**, because it describes the vulnerability in
the abstract and deliberately excludes how the component is used in your system.
Thresholding on it therefore selects an essentially arbitrary subset with
respect to the question actually being asked.

## 5.3 H2 — Ranking quality

| Ordering | Mean Average Precision |
|---|---|
| DepSentry (reachability-aware) | **0.950** |
| CVSS only | 0.512 |

An **85.6% relative improvement**. A CVSS-only ordering places exploitable
findings at roughly the position random ordering would (MAP ≈ prevalence-driven
0.512); DepSentry places them near the top.

This matters more than the volume reduction in practice. Developers work queues
top-down and stop when time runs out. Under CVSS ordering, the work done first
is largely wasted.

**H2 is supported.**

## 5.4 Ablation — which signal is doing the work?

| Variant | Precision | Recall | F1 | Alerts |
|---|---|---|---|---|
| Full DepSentry (reachability + risk ≥ 4.0) | 1.000 | 0.930 | 0.964 | 80 |
| **Reachability filter only** | **1.000** | **1.000** | **1.000** | 86 |

This is the most informative result in the study, and it is partly a **negative
result about our own design**.

The reachability filter alone is perfect on this corpus. Adding the risk ≥ 4.0
threshold **costs 6 true positives and gains nothing** — precision was already
1.000, so there were no false positives left to remove.

Investigating the 6 false negatives: **all six are the same advisory**,
`DEPS-2026-0021` (CVSS 3.3, terminal escape injection in `click.echo`),
reachable in 6 projects. Its fused risk is 3.62, just under the 4.0 threshold.

So the entire recall loss is one LOW-severity advisory suppressed by a threshold
that contributed no benefit. Two honest readings:

1. **The threshold is defensible.** A CVSS 3.3 issue arguably *should* sit below
   an action threshold; the tool is behaving as designed and surfacing it in the
   suppressed-findings list rather than deleting it.
2. **The threshold is unjustified by this evidence.** It was chosen a priori to
   align with the CVSS MEDIUM boundary, and the data shows it purchasing nothing
   on this corpus.

We report reading 2 as the finding and retain the threshold as configurable
rather than silently tuning it to 3.5 to claim recall 1.000. Tuning a parameter
against the test set after seeing the result would inflate the headline number
without improving the method — the outcome would be a better-looking table and a
less honest one.

## 5.5 Reachability distribution

| Verdict | Count | Share |
|---|---|---|
| REACHABLE | 86 | 33.2% |
| UNREACHABLE | 173 | 66.8% |

**Two thirds of matched advisories are not reachable from any entrypoint.** This
is consistent with the widely reported industry observation that only a minority
of dependency CVEs sit on an executed path, and it quantifies the scale of the
waste in package-level scanning.

Note that no POTENTIALLY_REACHABLE or UNKNOWN verdicts appear. Both paths are
implemented and unit-tested, but the generated corpus contains no dynamic
dispatch and every advisory carries symbol data. That is a property of the
benchmark, not evidence those paths are unused — and it is a limitation, below.

## 5.5b Live validation against real OSV data — the blocking obstacle

Sections 5.2–5.5 use the synthetic corpus. This section reports what happened
when DepSentry was pointed at **real advisories from OSV.dev** (`--live`), and it
is the most consequential result in the project.

### Measurement: PyPI advisories carry no symbol data

Reachability analysis needs to know *which function* an advisory affects. OSV
has a field for this — `affected[].ecosystem_specific.imports[]`, carrying
`path` and `symbols`.

Measured twice, at two scales (2026-07-31):

| Source | Advisories | With symbol data |
|---|---|---|
| PyPI — exploratory sample (requests, urllib3, django, pyyaml, jinja2, numpy, pillow) | 171 | **0 (0%)** |
| PyPI — full benchmark corpus, 16 packages (`experiments/evaluate_live.py`) | 121 | **0 (0%)** |
| Go (`GO-` vulndb) | spot-checked | populated — e.g. `GO-2021-0053` lists `["unmarshal.Generate", "unmarshal.field"]` |

The field exists and the Go ecosystem populates it well. **The Python advisory
sources do not populate it at all.**

### Consequence: the core contribution is inert against live PyPI data

Running the **full 40-project benchmark against real advisories**
(`experiments/evaluate_live.py`, results in `reports/evaluation_live.md`):

| | Upstream symbols only | With curated overlay |
|---|---|---|
| Total findings | 1,349 | 1,349 |
| CVSS ≥ 7.0 gate would alert | 518 | 518 |
| DepSentry actionable | **0** | 468 |
| **Unassessable (UNKNOWN)** | **1,349 (100%)** | 116 (8.6%) |

**Without a symbol overlay, DepSentry assesses nothing and surfaces nothing.**
Not "performs poorly" — produces no verdict at all, on every one of 1,349 real
findings.

Two further observations:

- **Real alert load is 5.2× the synthetic corpus** (1,349 vs 259 advisory
  instances over the same 40 projects). The triage problem is worse in reality
  than the benchmark suggests.
- **With the overlay, volume reduction against the CVSS gate is 518 → 468, only
  9.7%** — far below the 25.2% measured on synthetic data. Overlay symbols are
  coarse (a package's whole dangerous API surface, not one advisory's specific
  function), so they over-attribute reachability. This is the expected direction
  for a heuristic that errs toward false positives, and it is the honest ceiling
  on what the overlay can deliver.

This is the honest headline for real-world deployment today: *the method is
sound, and the data needed to run it does not exist for Python.* The 100%
precision reported in §5.2 describes conditions — full symbol coverage — that
live PyPI advisories do not currently provide.

### A bug this exposed in our own headline metric

The first live run printed **"noise-cut 100%"** while having assessed nothing.
`noise_reduction()` divided suppressed findings by *all* findings, and UNKNOWN
findings — the ones we explicitly could not evaluate — were counted in the
numerator as though they had been safely ruled out.

That is a silent false negative wearing the headline metric's clothes, and it
was invisible under the synthetic corpus because that corpus has 100% symbol
coverage and therefore produces no UNKNOWN verdicts at all. The metric now
divides over **assessed findings only**, and the console surfaces a separate
`needs-review` count that cannot be confused with suppression.

The synthetic benchmark could not have caught this. Only real data did.

### Mitigation and its honest limits

`data/symbol_overlay.json` provides a curated advisory-ID → symbols map, with an
opt-in package-level heuristic (`--overlay-heuristic`) that attributes a
library's known dangerous API surface to any advisory on that library. With the
heuristic enabled, the same live scan resolves **8 REACHABLE findings with real
call paths** against genuine GHSA and PYSEC identifiers.

**The heuristic is a guess, not a fact**, and the design reflects that: it is
off by default, every finding records its `symbol_source` (`upstream` /
`overlay` / `none`), and coverage statistics print on every live scan. It errs
toward marking findings REACHABLE — a false positive — rather than hiding them.

### What this changes about the project's claims

1. The reachability method is **validated in principle** and **blocked in
   practice for PyPI** by upstream data availability.
2. The single highest-value contribution this project could make to the
   ecosystem is not a better analyser — it is **advisory symbol data**.
   Go's vulndb demonstrates the format is workable at scale.
3. Future work item #1 (real-project validation) is now revised: it must be
   paired with symbol curation, because the advisories alone will not support it.


## 5.6 Threats to validity

Stated plainly, because a results chapter that only reports favourable framing
is not a research result.

### Construct validity — the most serious limitation

**The benchmark is generated by the same notion of reachability the analyzer
implements.** The generator writes a call to the vulnerable symbol, and the
analyzer detects that call. The perfect ablation score (P = R = 1.000) therefore
measures **implementation correctness**, not real-world difficulty.

Real codebases contain the hard cases the corpus lacks: dynamic dispatch,
framework-mediated invocation, dependency injection, callbacks passed as values,
monkey-patching, conditional imports, C extensions. Against real projects,
performance would be **materially lower**.

The honest claim this experiment supports is: *the pipeline correctly implements
reachability-aware prioritisation, and where reachability is statically
determinable it substantially outperforms CVSS thresholding.* It does **not**
support a claim of 100% accuracy on production software, and that claim is not
made anywhere in this project.

### Internal validity

- **Advisory corpus is synthetic** (`DEPS-` identifiers, 30 advisories).
- **Symbol coverage is 100% in the corpus and 0% in live PyPI data** — measured,
  not estimated (§5.5b). An earlier draft of this document guessed "perhaps
  20–40%"; the real figure for PyPI is zero. Coverage directly caps how much of
  the benefit is achievable, so on live PyPI data today the achievable benefit
  without a symbol overlay is nil.
- **Risk-fusion weights are unvalidated.** The multipliers are reasoned, not
  learned. The ablation shows the result is driven by reachability, so the
  weights are not load-bearing for the headline — but they are not evidence-based
  either.

### External validity

- Python only. Ecosystems with heavier reflection (Java) or aggressive tree
  shaking (JavaScript) would behave differently.
- Generated projects are structurally simpler than production applications.
- No human study: whether the volume reduction improves real remediation
  outcomes is untested.

### Statistical

- Single seed (42). No confidence intervals across seeds.
- 40 projects, 259 instances — adequate for the effect size observed, but small.

## 5.8 Conclusions

1. **Reachability is a stronger prioritisation signal than severity.** Precision
   1.000 vs 0.318; MAP 0.950 vs 0.512.
2. **Two thirds of matched advisories are inert** in the codebase that pulls
   them in.
3. **CVSS thresholding is a poor triage rule** — recall 0.395 means it misses
   most of what matters while raising 73 false alarms.
4. **The severity threshold added to reachability was unnecessary** on this
   corpus, costing recall for no precision gain (§5.4).
5. **The measured performance is an upper bound.** The synthetic benchmark
   validates the implementation; it does not establish real-world accuracy.
6. **Against live PyPI advisories the method currently cannot run**, because
   0 of 171 sampled advisories carry the symbol data it depends on (§5.5b). The
   bottleneck is advisory data, not analysis technique.

## 5.9 Future work

Ordered by what would most strengthen the claim:

1. **Advisory symbol curation.** Now the top priority, ahead of real-project
   validation — §5.5b shows the latter is blocked without it. Curate
   advisory-ID → symbol mappings for the most-depended-on PyPI packages and
   contribute them upstream. Go's vulndb proves the format works at scale.
2. **Real-project validation, paired with curation.** Manually label
   reachability for 10–20 real open-source projects against genuine OSV
   advisories plus curated symbols. This attacks the construct-validity
   limitation, but cannot proceed on advisories alone.
3. **Inter-procedural and framework-aware analysis.** Resolve dependency
   injection and decorator-mediated invocation to shrink the
   POTENTIALLY_REACHABLE class.
4. **Cross-seed statistics.** Repeat over 30 seeds; report confidence intervals.
5. **Learned risk weights.** With real labelled data, replace the reasoned
   multipliers with a fitted model.
6. **VEX output.** Emit machine-readable "not affected" justifications backed by
   call-path evidence.
7. **Multi-language support.** Java bytecode analysis would test the approach in
   a reflection-heavy ecosystem.
